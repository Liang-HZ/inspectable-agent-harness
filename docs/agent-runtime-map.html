我们现在做到了什么

这个项目已经不只是一个“调用模型的接口”。它现在有了一个小而完整的 Agent runtime spine：能接请求、流式调用模型、接受工具调用、执行工具、写回工具结果、继续模型轮次、产出最终答案，并把过程记录下来。

模型调用

支持 OpenAI-compatible 的 chat.completions 和 responses 两种 wire API。runtime 不直接看 provider 原始字段，而是通过 dialect 消化成统一事件。

Agent Loop

每一轮都是一次 streaming sampling round。没有 tool call 的那轮就是最终答案，不再额外调用一次模型生成总结。

工具系统

当前工具面聚焦真实 local file 探查： ls、find、grep、read。

流式输出

后端发出 assistant_delta，路由投影成前端 SSE 的 assistantDelta。UI 是观察者，不执行工具，也不调用模型。

历史和回放基础

streaming run 会写 JSONL session：session_meta、turn_context、agent_event、response_item。

测试基础

有 fake AgentModelGateway 的 deterministic sampling-loop 测试，也有真实 built-in tool runtime 测试，覆盖成功、错误、截断和集成链路。

流式 Agent 数据链路

这是从浏览器点击提交到最终答案返回的完整链路。读这个时重点看数据在每一层变成什么。

1

用户提交任务

React 组件收集 task / goal / context / model / temperature，创建 AbortController。

数据形态：浏览器里的表单状态。

2

浏览器 client 发起 SSE 请求

lib/agent-api-client.ts 调用 POST /api/agent/stream，并逐行解析 SSE。

数据形态：HTTP request body，之后变成前端事件 callback。

3

Route 做边界处理

app/api/agent/stream/route.ts 读取 JSON，调用 parseAgentInput，读取 model config，然后进入 runAgentStream。

数据形态：unknown 请求体变成已校验的 AgentInput。

4

创建 run context 和 session

runAgentStream 创建 AgentRunContext 和 JSONL session，写入 session_meta、turn_context。

数据形态：运行时上下文、append-only session 文件。

5

构造初始模型历史

把系统提示和用户任务变成 AgentResponseItem[]。

数据形态：message(system) 和 message(user)，它们会被持久化为 response_item。

6

进入 sampling round

responseItemsToModelMessages 把 history 转成 AgentModelMessage[]。

数据形态：provider-neutral model request，包括 messages、tools、toolChoice、temperature。

7

Dialect 编译 provider 请求

OpenAI Chat dialect 把 tools 编译成 { type: "function", function: ... }；Responses dialect 编译成 { type: "function", name, parameters, strict }。

数据形态：provider wire request。runtime 本身不知道这个格式。

8

Provider stream 变成统一事件

Dialect 把原始 stream chunk 转成 AgentModelStreamEvent：text_delta、assistant_message_done、tool_call_delta、tool_call_committed、completed。

数据形态：provider-neutral stream event。

9

runtime 发内部事件

text_delta 会变成 assistant_delta，同时累积本轮的 assistant text。

数据形态：AgentEvent。stream route 再投影成前端 SSE 的 assistantDelta。

10

round 结束后做决策

如果本轮有 tool_call_committed，它是工作轮；如果没有 tool call，它就是最终答案轮。

数据形态：SamplingRoundResult，包含 assistantMessages、toolCalls、usage。

11

工具轮执行工具

runtime 写入 working assistant message 和 function_call，然后调度工具 batch。tool runtime 负责 permission、started、finished、错误转 tool output。

数据形态：function_call 和 function_call_output 进入 history。

12

继续或结束

有工具结果就进入下一轮模型调用；没有工具调用的 round 直接把 committed assistant text 当最终答案。

数据形态：AgentResult，包含 answer、steps、usage。

Sampling Loop：为什么它不是普通 while

这里的 sampling 指“一次模型生成调用”。Sampling loop 指“模型生成 -> 可能执行工具 -> 带着工具结果继续生成”的循环。

Sampling Round

一次 round 只负责消费一次模型 stream。它不执行工具，只收集结果。 

stream model
collect text_delta
collect assistant_message_done
collect tool_call_committed
collect completed usage
return SamplingRoundResult

Sampling Loop

loop 负责根据 round result 改写 history、执行工具、决定是否继续。 

for round in 1..:
  roundResult = runSamplingRound(history)
  if roundResult.toolCalls is empty:
    append final assistant message
    return final answer
  append working message + function_call
  execute tool batch
  stop if identical tool loop repeats
  append function_call_output
  continue
关键点： 最终答案不是额外补一次模型调用生成的。最后一个没有 tool call 的 sampling round，本身就是最终答案 round。这个设计来自我们对 Codex CLI 和 pi-mono 的对照调研。

模型可见历史：AgentResponseItem

当前 runtime 的核心资产不是 UI step，而是 provider-neutral 的模型可见 history。它决定下一轮模型实际能看到什么。 

type AgentResponseItem =
  | {
      type: 'message';
      role: 'system' | 'user' | 'assistant';
      content: string;
      providerPhase?: 'commentary' | 'final_answer' | null;
      runtimeRole?: 'working_message' | 'final_response';
    }
  | {
      type: 'function_call';
      callId: string;
      name: string;
      argumentsJson: string;
    }
  | {
      type: 'function_call_output';
      callId: string;
      toolName: string;
      output: string;
      isError: boolean;
    };
Item 什么时候产生 下一轮模型是否可见 为什么重要
message(system) run 开始时创建。 可见 约束 agent 行为、工具使用策略、回答语言。
message(user) 把 AgentInput 组装成 prompt 后创建。 可见 承载用户任务、目标和上下文。
message(assistant) 模型完成一条 assistant message 后提交。 可见 可能是工作说明，也可能是最终答案，取决于同一 round 是否有 tool call。
function_call 模型提交工具调用后创建。 可见 保持模型自己请求过什么工具的完整上下文。
function_call_output 工具执行完后创建。 可见 模型下一轮据此继续推理、重试或最终回答。

Debug Console v1 会显示每轮模型 input 和 output、history commit、工具参数、模型可见 tool output、内部 details 和 usage。浏览器仍然只是观察者，不执行工具。history commit 通过 stream-only debug 事件展示，不写入 JSONL 的 agent_event；JSONL 里的权威上下文仍然是 response_item。

当前前端把同一条 run 分成 Agent、Debug 和 Session 三个页面：Agent 页面用用户可理解的“模型输出 / 使用工具”串联 assistant 文本和同批 tool calls，不暴露 round 这类 runtime 术语；Debug 页面保留完整 request/output/details 供排查；Session 页面直接读取当前 run 的真实 JSONL 落盘记录。

Provider Dialect：模型供应商怎么接进来

runtime 只认 Agent IR。不同模型 API 的差异在 dialect 里解决。

Agent IR OpenAI Chat Completions OpenAI Responses 未来 Anthropic
AgentModelMessage[] messages input messages + 独立 system
AgentModelToolDefinition.inputSchema function.parameters parameters input_schema
schemaStrict function.strict strict 忽略或映射成兼容策略
text_delta delta.content response.output_text.delta text delta block
tool_call_delta delta.tool_calls[index].function.arguments response.function_call_arguments.delta tool_use input delta
tool_call_committed finish_reason="tool_calls" 后重组 response.output_item.done(function_call) 完整 tool_use block
为什么刚改成 inputSchema/schemaStrict： 这让工具契约属于 agent runtime，而不是 OpenAI。OpenAI dialect 只是把它翻译成 parameters/strict。以后 Anthropic dialect 可以翻译成 input_schema，不用污染 runtime。
OpenAI strict schema 的特殊规则： OpenAI 要求 strict tool schema 里每个 properties 字段都出现在 required 中，optional 字段用 type: ["number", "null"] 这类形式表达。这个转换由 lib/openai-tool-schema.ts 在 OpenAI dialect 边界完成；runtime 的 Zod 解析再把 optional 的 null 归一成 undefined。

工具系统：现在有哪些能力

工具系统当前重点是内置只读 local file 探查。我们故意还没有做 bash 和 edit，因为它们会引入 sandbox、审批、并发写入和进程管理复杂度。

工具 参数 输出 安全边界
ls path?、limit? 目录 entries，按名称稳定排序。 当前 project-root path policy，忽略 .git、.next、node_modules。
find pattern、path?、limit? 匹配文件路径，limit notice。 只递归当前允许根目录内文件，不跟随 symlink 逃逸。
grep pattern、path?、glob?、ignoreCase?、literal?、limit? path、lineNumber、line，超限时给 refine notice。 通过本机 rg 搜索当前允许根目录内文件。
read path、offset?、limit? line metadata、content、pagination notice。 只读 UTF-8 文本文件，50KB 输出上限。

工具调用的数据链路

Model emits tool_call_committed
  -> AgentResponseItem(function_call) is appended
  -> AgentToolScheduler chooses parallel or sequential
  -> AgentToolRuntime creates permission request
  -> decideAgentToolPermission returns allow / ask / deny
  -> concrete tool parses JSON arguments with Zod
  -> handler returns AgentToolOutput or throws a typed tool error
  -> runtime serializes AgentToolOutput into plain modelOutput text
  -> AgentResponseItem(function_call_output.output = modelOutput) is appended
  -> next model round sees the tool result

工具结果契约

工具内部结果是结构化的，但模型历史里的 function_call_output.output 永远是纯文本。这样模型不用解析 {ok,error,details} 这样的 envelope，UI 和日志又不会丢失结构化 details。 

type AgentToolOutput =
  | {
      type: 'success';
      contentText: string;   // 给模型看的正文
      details?: unknown;     // 给 UI / 日志 / 测试看的结构
      notice?: string;       // 序列化时追加成 [notice]
    }
  | {
      type: 'respond_to_model';
      error: { code: AgentToolErrorCode; message: string };
      details?: unknown;
    }
  | {
      type: 'fatal';
      error: { code: AgentToolErrorCode; message: string };
      details?: unknown;
    };

success          -> contentText + optional "\n\n[notice]"
respond_to_model -> "Error [CODE]: message"
fatal            -> terminate run, no function_call_output

TIMEOUT 和运行中的 ABORTED 会作为 recoverable tool output 写回 history，让下一轮模型知道工具没有正常完成。 这和 unknown tool、参数错误、路径越界属于同一类：反馈给模型，而不是把整个 agent loop 直接炸掉。

并行策略

当前 scheduler 不猜数据依赖。它只看工具 metadata：一个 batch 里的所有工具都声明 executionMode="parallel"，才用 Promise.all 并行执行。即使并行，输出也按模型原始 tool call 顺序写回 history。

JSONL Session：为什么要记录过程

Session 文件不是普通日志。它是未来 resume、replay、debug、评测的基础。现在 streaming run 会写模型可见 history 和 runtime events。 

{"type":"session_meta","payload":{"id":"...","cwd":"...","model":"..."}}
{"type":"turn_context","payload":{"turnId":"...","wireApi":"openai-responses"}}
{"type":"response_item","payload":{"type":"message","role":"system","content":"..."}}
{"type":"response_item","payload":{"type":"message","role":"user","content":"..."}}
{"type":"agent_event","payload":{"type":"run_started","runId":"..."}}
{"type":"response_item","payload":{"type":"function_call","name":"read","argumentsJson":"..."}}
{"type":"response_item","payload":{"type":"function_call_output","toolName":"read","output":"File: ...","isError":false}}
{"type":"agent_event","payload":{"type":"run_succeeded","result":{"answer":"..."}}}

当前有 GET /api/agent/sessions 和 GET /api/agent/sessions/:id 用于本地检查 session，但还没有 resume。前端 Session tab 也是通过 这个只读 API 打印 JSONL，一行对应一个真实 session record。

Token Usage：raw 和 normalized 同时保留

单次 token 数来自 provider，跨轮总数由 runtime 累加。缓存 token 用 null 表示 provider 没报告，而不是假装成 0。 

type AgentTokenUsage = {
  inputTokens: number;
  cachedInputTokens: number | null;
  outputTokens: number;
  reasoningOutputTokens: number;
  totalTokens: number;
};
字段 语义
rawUsage provider 原始 usage，保留细节，便于排查中转站或不同 API 的字段差异。
tokenUsage runtime 统一后的 usage，供 UI 和总计使用。
calls 每一轮 sampling call 的 usage 记录。
totalTokenUsage runtime 对所有有 usage 的 call 做聚合。

演化时间线

这个项目不是一次性设计出来的。它是从最小可运行模型调用，一层一层把真实 agent 需要的边界补出来。

Phase 0：OpenAI-compatible Chat API

先做最小可运行路径：route、input parser、env、SDK client、service。目的不是 agent，而是先把后端分层立住。

Phase 1：小型可检查 Agent

加入 /api/agent 和 /api/agent/stream。最早曾用 toy tool 验证工具链路，后来在 read-only built-ins 落地后移除。

Phase 2：结构化日志和 steps

加入 runId、prompt、step output、tool output 的服务端日志。我们开始能看见 runtime 做了什么。

Phase 3：Streaming 输出

后端发 runtime event，route 投影成 SSE，前端只观察。assistantDelta 代表 assistant 输出，不提前承诺 final。

Phase 4：Cancellation Boundary

AbortController、fetch signal、NextRequest.signal、AgentRunContext、SDK request options 串成真正的取消链。

Phase 5：Harness Direction

明确模型不是 agent。Agent 是模型外面的 runtime harness，负责工具、权限、事件、session、取消和未来 resume。

Phase 6：Tool Runtime Boundary

工具执行从 agent.ts 拆到 agent-tool-runtime.ts，让编排和工具生命周期分离。

Phase 7：Permission Skeleton

把 tool annotations、approval policy、sandbox mode 分开。现在只是骨架，但方向是对的。

Phase 8：JSONL Session

引入 Codex-style rollout 的简化版。先记录事件，后来加入模型可见 response_item。

Phase 9：Session Read APIs

增加 session list 和 detail API，便于不用手动翻文件也能检查 run。

Phase 10：Usage Tracking

规范 token usage：provider raw usage 保留，runtime normalized usage 用于汇总。

Phase 11：Provider Dialect

把 OpenAI Chat/Responses 的差异关进 dialect，runtime 只消费 AgentModel IR。

Phase 13：Agent Runtime Spine

固定两次调用被替换为真实 loop：history、tool call、tool output、继续模型，直到没有 tool call。

Phase 14：Streaming Sampling Loop

每一轮都改成 streaming sampling round。最终答案来自最后一轮自然输出，不再额外总结调用。

Phase 15：Assistant Message Commit

区分 text_delta、assistant_message_done 和 round decision。流式过程可显示，round 结束后才判断是否 final。

Phase 16：Deterministic Loop Tests

用 fake gateway 做模型无关测试，验证 history shape、protocol error、tool loop。

Phase 17：Built-In Read-Only Tools

加入 ls/find/grep/read，不再只靠玩具工具。它们有 当前 project-root path policy、limit notice 和真实 runtime 测试。

Phase 18：Agent-owned Tool Contract

工具 IR 从 OpenAI 字段名中抽出来，使用 inputSchema/schemaStrict。OpenAI dialect 再映射成 parameters/strict。

Phase 19：OpenAI Strict Schema Adapter

OpenAI strict tools 要求所有 properties 都进 required，optional 用 null 类型表示。这个转换被关进 OpenAI dialect 边界。

Phase 20：Frontend Debug Console

前端开始展示每一轮模型输入、工具 lifecycle、模型可见 modelOutput、内部 details 和 usage，用来验证 agent runtime。

Phase 21：Agent / Debug / Session 页面拆分

Agent 页面改成用户视角的过程流：模型文本和工具批次串联展示，steps 收起作为摘要。模型文本按 Markdown 渲染，支持列表、表格和代码块。 Debug 页面保留完整可滚动的 JSON 和文本 payload。Session 页面 打印当前 run 的 JSONL，方便对照真实 resume/replay 记录。

Phase 22：Tool Runtime Boundary v1

工具定义拆出 source/group/category、 pathAccess、executionMode、 timeoutMs 和 abortable。当前只激活 utility_builtins 与 read_only_builtins，editing_builtins 和 shell_builtins 先作为空骨架。

关键决策

为什么先做 read tools，不先做 bash

Bash 会立刻引入 OS sandbox、审批、timeout、PTY、输出流、网络和写操作风险。read tools 能先验证真实工具链路，又把安全面控制住。

为什么不猜工具数据依赖

runtime 无法可靠知道 A 的输出是否被 B 依赖。模型需要依赖时，应分两轮请求。scheduler 只根据工具 metadata 决定一个已提交 batch 是否可并行。

为什么保留 response_item

steps 是展示，response_item 是模型历史。未来 resume、compaction、replay 都依赖模型可见历史，而不是 UI 展示文本。

为什么 final answer 不额外调用模型

成熟 agent 通常让模型在最后一个无工具调用 round 自然输出最终答案，UI 再做视觉区分。额外总结调用会增加延迟和语义不一致。

为什么 dialect 是数据库方言式边界

runtime 的 IR 像查询 AST，不同 provider 像不同 SQL 方言。这样 Anthropic、OpenAI、兼容中转站都不会污染 agent loop。

为什么 cached token 用 null

0 表示 provider 明确报告没有缓存命中，null 表示 provider 没报告字段。这两个语义不能混。

还没做什么

这些不是失败项，而是后续扩展点。现阶段我们先把 spine 和 read-only 工具体系做稳。
